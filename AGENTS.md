# AGENTS.md

## Project overview

`@rbxts/toucan` is an opinionated Entity Component System framework for Roblox-TS, inspired by Bevy and favoring developer experience over raw performance. It is built on top of `@rbxts/jecs` and heavily depends on it. It is in alpha and not yet production-ready.

## Communication

- Prefer concise responses for code changes over conversational explanations. Summarize what changed and why; skip lengthy narration.

## Toolchain & commands

- The package manager is **bun** (enforced by `preinstall: only-allow bun`); never use npm, yarn, or pnpm.
- `bun run setup` — installs dependencies for the root, `test/`, and `docs/`, then runs `rokit install`.
- `bun run build` — compiles with `rbxtsc` into `out/` (the published artifact).
- `bun run dev` — runs `rbxtsc -w`, the test project's `rbxtsc -w`, and `rojo serve` concurrently.
- `bun run lint` / `bun run format` — Biome (`check --write` / `format --write`).

## Repository layout

- `src/` — library source. `src/index.ts` is the public API surface.
- `test/` — a separate roblox-ts project. Tests run inside Roblox via rojo, not in Node.
- `docs/` — Astro/Starlight site. The API reference is generated by `starlight-typedoc` from `src/index.ts`.

## Code conventions

**Formatting & linting**

- Biome is the source of truth: run `bun run lint` before finishing; don't hand-format.
- Biome also rewrites type-only imports to `import type` automatically.

**Naming**

- Components and resources are PascalCase nouns (`Age`, `Health`, `System`, `Plugin`).
- Anything outside the public API is `_`-prefixed (`_simulateThirdParty`, `_despawn`, `_inSets`).

**Scope of changes**

- Prefer localized changes over large ones that cover multiple areas of the codebase.
- Never make changes that aren't related to what was asked, like unrelated bugs you encounter midway. Instead, simply mention them.

**Public API & TSDoc**

- The public surface is `src/index.ts`; new public symbols must be exported there.
- Every new public symbol needs a TSDoc block with a valid `@group` tag — `Core`, `Types`, or `Built-ins` (these drive the generated API docs).
- Mark anything not re-exported from `src/index.ts` with `@internal` (stripped from `.d.ts` via `stripInternal`).
- Use `@example` for user-facing functions and `@remarks` for caveats.

**Errors**

- Use Luau `error(...)` / `assert(...)`, not `throw`.
- Actionable messages end with `\n\nTip: ...`.
- Use `error('Unreachable')` in exhaustive branches.

**Types (roblox-ts)**

- Never use `any`; prefer `unknown`, and `defined` when `undefined` must be excluded.
- This is a roblox-ts project (`noLib: true`): no Node/DOM globals. Use Luau globals directly — `error`, `assert`, `typeOf`, `typeIs`, `tostring`, `pairs`, `os.clock()`.
- Runtime type checks use `typeOf` / `typeIs`, not `typeof`.
- Import Roblox services from `@rbxts/services`; the ECS core is `@rbxts/jecs`.
- Prefer `task.*` / `os.clock()` over the deprecated `wait` / `spawn` / `delay` / `tick`.

**Comments**

- Explain _why_, not _what_ — non-obvious constraints and tradeoffs get a comment; restating the code doesn't.

**Circular dependencies**

- Imports must flow one direction; break cycles with dedicated context/registry modules instead of back-imports (e.g. `entities/builtinRegistry.ts`, `scheduler/pluginContext.ts`, `scheduler/systemContext.ts`).
- `import type` is safe across a cycle (erased at compile time); value imports are not.

## Testing

- Tests live in `test/src/server/*.test.ts` and use `@rbxts/lunit`.
- **You cannot run the tests yourself.** They execute inside Roblox and there is no headless runner; a human must open Roblox Studio (via `bun run dev` / `rojo serve`) and run them manually. Don't attempt `bun test` or similar.
- What you _can_ verify on your own: `bun run build` (type-checks the library with `rbxtsc`) and `bun run lint`. Run these before handing work back.
- `test/src/server/runTests.server.ts` is currently a scratch/manual script (its `TestRunner` is commented out); don't treat it as a runnable suite.
- When a change needs runtime verification, say so and ask the user to run the tests in Studio.
